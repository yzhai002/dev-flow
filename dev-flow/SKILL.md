# Dev Flow

根据任务规模路由到两条流水线之一。判断必须在动手之前完成，并且先把判断结果和理由告诉用户，再进入对应流水线。

## 第一步：判断任务类型

结合用户输入、相关代码和 issue 内容分类：

**小型（全自动闭环）** —— 需同时满足：

- 根因明显，改动集中在少数文件
- 无数据 / schema / API 兼容性风险
- 不涉及安全、并发、跨服务
- 现有测试可覆盖，或补测试成本低

**大型（分析为主，带人工门禁）** —— 命中任意一条即算大型：

- 根因不明，需要先复现排查
- 影响核心业务逻辑、数据正确性或资金
- 涉及安全漏洞、并发竞态、数据迁移
- 波及多个服务或大范围用户
- 线上事故（P1 / P2 级别）

不确定时一律按大型处理——小型误判为大型只是多花一步确认，大型误判为小型可能直接改坏生产代码，成本不对称。

做到一半发现判断错了（按小型开工后发现是大型）：立即停手，已做的工作并入分析材料，切换到大型流水线重新走。

## 小型流水线（全自动，一路到底）

Issue → Branch/Worktree → Code → Test → Merge → Release

1. **Issue**：用户给了 issue 链接或编号就读取（`gh issue view`）；没给就在收尾总结中说明本次修复内容，必要时补建 issue。
2. **Branch/Worktree**：从最新主干切 `fix/<slug>` 分支。工作区有未提交改动、或需要与其他工作并行时，用 `git worktree`；否则直接建分支。
3. **Code**：最小改动修复，风格对齐周围代码。
4. **Test**：运行相关测试；为修复点补一个回归测试。测试不过不得继续。
5. **Merge**：`gh pr create` → CI 绿 → merge（默认 squash，遵循仓库既有惯例）。
6. **Release**：跟随仓库既有发布方式——已有 tag / `gh release` / CD 流水线就按其执行；没有现成方式就打 tag 并在总结中说明。

完成后给用户一条总结：根因、改动点、测试结果、PR 与 Release 链接。

## 大型流水线（两个人工门禁，门禁通过前不改生产代码）

Issue → Reproduce → Impact Analysis → Root Cause → Fix Plan → **[人工确认 ①]** → Branch/Worktree → Code → Test/Regression → Review → **[人工确认 ②]** → Canary Release → Monitor → Release

### 阶段 A：分析（只读，不动任何生产代码）

1. **Reproduce**：尽力复现——本地、测试环境，或从日志还原现场。复现不了就明确写"未复现"，并列出已排除的假设。
2. **Impact Analysis**：影响面——哪些功能 / 用户 / 数据受影响，是否正在恶化，是否需要先止血（回滚、降级、功能开关）。止血建议属于分析产出，不是改代码。
3. **Root Cause**：定位到具体代码行或提交，用证据支撑（日志、堆栈、diff、复现实验），不靠猜。
4. **Fix Plan**：写出方案——改动文件清单、测试与回归范围、发布策略（含金丝雀方案）、回滚方案。

然后**停下**，向用户提交完整分析报告，等待人工确认 ①。未经确认不得创建修复分支、不得修改任何生产代码。

### 阶段 B：实施（确认 ① 之后）

5. **Branch/Worktree**：切 `fix/<slug>` 分支（或 worktree）。
6. **Code**：严格按已确认的 Fix Plan 实施；实施中需要偏离方案时，先说明原因并征得用户同意。
7. **Test/Regression**：修复点的针对性测试 + 受影响范围的回归。如实报告结果，红就是红。
8. **Review**：自查 diff，逐条对照 Fix Plan；然后 `gh pr create`，PR 描述中附分析摘要，请求 review。

然后**停下**，等待人工确认 ②（review 通过且用户放行）。

### 阶段 C：渐进发布（确认 ② 之后）

9. **Canary Release**：按团队发布通道先放小流量；没有现成金丝雀机制时，先部署到预发或单实例，并明确告知用户这视为金丝雀。
10. **Monitor**：盯关键指标——错误率、延迟、相关业务指标、日志报错。发现异常立即停止发布并回滚（回滚是安全操作，果断执行，事后报告）。
11. **Release**：指标稳定后全量发布，打 tag / release，给出收尾总结。

## 收尾总结格式（两条流水线通用）

- 任务类型判定 + 理由
- 根因 / 改动点
- 测试结果
- 发布状态与链接（PR、tag、release）
- 大型任务额外附：完整分析报告、两次人工确认的记录
